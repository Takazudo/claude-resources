# zproto

Read [the workflow contract](workflow-contract.md) and [the delivery rules](delivery.md). Save each round’s created deliverable files as they are produced.

1. Do a light source review for stack, tokens, components, content, and constraints. Write a shared brief with target interactions, responsive states, realistic worst-case content, and accessibility needs.
2. Build each round as one self-contained HTML/CSS/JS page with an in-page switcher for its variants and for the states that matter (data volume including empty and worst case, API limits, phone width, light/dark). Preview it as a **private Artifact** when the Artifact tool is available, republishing later rounds to the same artifact so the user keeps one link with version history; otherwise send the HTML and screenshots with `SendUserFile`. Never share an Artifact or publish publicly without the user's intent: prototypes may contain private information. The round loop mechanics (brief, mock foundation copied from the real tokens, brainstorm vs polish spread) follow `$HOME/.claude/skills/big-plan/references/prototype-mode.md` §0–§6; its epic/issue/bake steps do not apply here.
3. For exploration, show meaningfully different options; for polish, make focused changes. Preserve round directories and identify variants so feedback can refer to earlier rounds.
4. Exercise available interactions and breakpoints, capture screenshots when possible, and inspect actual output. Label unexecuted checks and visual limitations. A screenshot alone does not supply editable source.
5. Present the result and wait for feedback each round. Iterate until the user explicitly accepts a direction. Never infer acceptance from silence or an iteration count. If no direction is accepted, offer continued iteration or a clearly deferred plan; do not finalize a pretend winner.
6. Record accepted behavior, content, hierarchy, states, and Added/Removed/Superseded feedback in `decisions.md`. Written accepted requirements outrank incidental prototype CSS. Production must use the repository's existing architecture, tokens, and reusable components.
7. Pass the accepted direction to zplan. Bundle complete accepted source, required assets, useful screenshots, and a short rationale for zdev's delivery channel. Preserve rejected rounds locally but exclude them from implementer-required resources unless comparison is necessary.
8. Write the accepted layout, content, behavior, states and user feedback in readable Chat and handoff text so implementation does not depend on opening the delivered prototype files. Keep truly essential exact assets identified separately. State concrete visual acceptance requirements (breakpoints, interactions, content extremes, and screenshots to compare) in the brief and handoff. A private preview URL supplements the transferable source; it never replaces it.
