# Standalone implementation handoff

## Producer checklist

Complete the accepted implementation brief in readable Chat and prompt text: goal, accepted UI and corrections, behavior/states, constraints and non-goals, acceptance criteria, components, dependency order, verification and actual permissions. The current zdev planning session and its delegated helpers perform read-only GitHub research. Do not create or change issues, epics, labels, comments, branches, commits or PRs, close or merge anything, or initiate GitHub-write approval requests here. Prepare the tracking structure and proposed issue content in the handoff. This session boundary does not restrict the separate implementation agent: require it to establish issue tracking before implementation, as specified in [implementation tracking](implementation-tracking.md).

Read current GitHub state before writing the prompt. Record actual issue and PR URLs, target branch and inspected SHA, existing bases/resources, checks already observed, and what is merely planned. Identify an existing matching tracker/epic and children for reuse when available; otherwise supply concrete titles, scope, acceptance criteria and dependencies for the implementing agent to create. Describe whether it should reuse/update a matching task PR or create a branch and draft PR. For multiple topics, give dependency order, integration checkpoints and explicit per-PR merge/hold decisions. Choose the simplest fitting implementation workflow. An explicit user restriction on new issues across implementation overrides the default: state the actual allowed tracking operations and adapt the template instead of emitting contradictory creation authority.

Follow [the delivery rules](delivery.md) for session-created deliverable files and the chosen channel (ZIP, Dropbox, `_temp-resource` draft PR). Delivered files are supplementary and contain real implementer-needed source/assets/fixtures when they exist; inspect and validate them. Otherwise state `Artifacts: none required`. Never imply that chat attachments, scratchpad paths or private Artifact previews are automatically accessible to another local or cloud session. Identify indispensable exact bytes and their destination-readable locator, or name the dependent blocker and continue independent planning.

Write for Codex, Claude Code, or Grok in the user's chosen local or cloud environment. The prompt must stand alone with the accessible repository and identified inputs. Translate every accepted flag and workflow decision into ordinary actions: the accepted scope, accepted UI direction, dependency order, merge authorized or not, and exact completion gates. Keep normalized flags in producer-side notes only. Do not include `zdev`, `zplan`, `zproto`, `zgh`, `zudo-dev-flow`, `big-plan`, `x-wt-teams`, `protodev`, plugin/app links, private skill invocations, planner-only flags, or instructions to use this planning flow in the execution prompt. Do not describe the planning Chat or its permissions inside the prompt. A repository or artifact name that happens to match a skill name is factual data, not an invocation. Inline the relevant procedure instead of referring to a skill. Resolve [execution environments](execution-environments.md) before final scope selection. Honor the deduplicated allowed set and explicit prose constraints, choose only sufficient allowed hosts, and name environment-excluded tasks with their unmet acceptance requirements. For unconstrained portable work explicitly state that this prompt can run in any supported environment. Use actual tools and models; do not invent orchestration APIs or model identifiers.

Inline [terminal resource cleanup](resource-cleanup.md) in **every** standalone implementation prompt, regardless of environment, merge flag or continuous mode. The final audit is part of the implementing session, not the read-only planning Chat. It must preserve uncommitted/user work, return the primary local checkout to a safe parent/default branch when possible, safely dispose only merged/unneeded owned resources, and report retained diffs and cleanup failures. When a child cannot delete a remote branch (for example Cursor working for a Grok bot manager), route the exact denied action to the parent for an independent, authorized safety-checked retry. Do not use a private skill invocation in place of the inlined steps.

Inline the environment contract from [execution environments](execution-environments.md). Only when Claude Code Cloud Project is selected, name its Project feature and inline the manager/child responsibilities from [Project execution](claude-code-cloud-project.md), including actual repository commit/push rules. Merely listing Project as an allowed candidate does not select its worker model. For a selected local CLI host, inline the local subagent procedure: one coherent substantive topic per subagent, capable configured model/effort, parent review/integration and sequential fallback. For Codex Cloud use only its actual worker facilities. For Grok CLI additionally inline its no-computer-use, smaller-task and verification constraints; for Grok bot cloud inline its cloud-only, actual-capability guard. For `-a`, inline [continuous development](continuous-development.md): first-wave tasks, repeatable inspect/plan/develop/review/verify/integrate/resweep steps, newly discovered in-scope defect handling, decision and blocker registers, a fresh-sweep end condition and durable continuation checkpoints. Do not append a second competing prompt or stop instructions at the first PR. Without merge authority, retain pending PRs/issues and continue independent work. Preserve explicit interview/prototype decisions, holds and all existing completion gates.

Before delivery, read the complete generated prompt as a new implementing agent. Verify that the terminal cleanup procedure is present **inside that prompt**, not solely linked or summarized outside it, and that cleanup does not incorrectly delete an unmerged branch or silently discard an unknown diff. Confirm that it can start tracking and implementation without this plugin, prior Chat history or unstated instructions; that it directs creation/reuse and ongoing updates of issues; and that no planning-only prohibition on issue creation remains. Check all user requirements and remove unresolved placeholders and inapplicable alternatives.

Select the merge-authorized branch when `-m`/`--merge` or an equally explicit user instruction requests it. State that the author wants the merge completed after development and its gates, including existing automatic updates to published websites or services. Inspect and describe those effects without adding a redundant generic approval gate. Without explicit merge intent, select the non-merge branch. Keep separate deployment actions and any concrete safety, permission or task-specific conflict distinct from the expected automatic effect of merging.
