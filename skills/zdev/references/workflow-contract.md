# zdev workflow contract

## Chat plan to a standalone implementation session

The current zdev planning session and every helper it delegates perform read-only GitHub research. Do not create or update issues, epics, labels, comments, branches or PRs; do not commit, push, close or merge, or initiate GitHub-write approval requests here. The single exception is the `-temp` delivery channel: when the user passes `-temp` or chooses it at the delivery question, create only the resource branch, its `_temp-resource/zdev-<slug>/` commit and one draft PR, as described in [delivery](delivery.md). Return a self-contained prompt plus necessary artifacts. This is a session-specific boundary, not a prohibition on issue tracking by the separate implementing agent.

Plan in the current Chat with `zdev`. Inspect repository instructions, source, issues, PRs and base SHA. Resolve ordinary choices and record assumptions, dependencies, acceptance criteria, review and verification. Use stable local task keys while planning; identify matching existing issues and prepare concrete issue content without posting it. The user starts a separate Codex, Claude Code, or Grok session, locally or in the cloud, with the final prompt. Chat does not claim to start or transform that session.

Require that implementing agent to establish tracking before changing implementation code: reuse or create one tracker for a focused task, or a parent epic plus linked sub-issues for multiple independently completable tasks. Include the full accepted requirements and keep meaningful decisions, progress, verification evidence, PR links, blockers and next actions in those issues throughout development. Close completed records according to their acceptance and integration requirements, children before parents. Follow [implementation tracking](implementation-tracking.md); issue creation is part of the requested execution, not an optional workaround or a new planning checkpoint.

Choose a fitting execution workflow. Big-plan and other orchestration patterns are design references only; the consumer need not know or install them. Simple cases need no artificial multi-PR topology. Task-specific user constraints override generic flag defaults. Match the user's environment, available tools and required platform verification.

Use `-pr` for a UI prototype and feedback loop. Show working variants when appropriate, preserve rounds, and wait for explicit acceptance before finalizing a direction. Put accepted behavior in readable Chat and prompt text. Deliver complete accepted source/assets through the chosen [delivery](delivery.md) channel (ZIP, Dropbox or a `_temp-resource` draft PR) when these files exist. Delivered files supplement the specification; they are not an entry prerequisite unless the user requires exact bytes. Identify indispensable missing inputs and continue independent work.

Use `-is` for a bulk-checkpoint issue sweep, `-isask` for the per-candidate interview including previously postponed issues, or `-a` for an explicitly authorized continuous sweep. When sweep modes combine, `-isask` wins for the interview; otherwise `-a` supplies routine in-scope acceptance without another bulk checkpoint. Follow [the sweep procedure](issue-sweep.md). Neither `-m` nor routine autonomy skips an explicit interview or prototype acceptance. Without `-a`, preserve the normal `-is` bulk checkpoint.

Resolve the deduplicated allowed environment set before selecting scope using [execution environments](execution-environments.md). With no environment constraint choose by requirements and explicitly keep host-independent work portable; one allowed host is a hard scope constraint, and multiple hosts are candidates from which to choose a sufficient host. Exclude work whose implementation or mandatory acceptance cannot complete within that set. Apply [Project execution](claude-code-cloud-project.md) only when Claude Code Cloud Project is selected; a candidate flag alone does not enable Project instructions. Selected local CLI environments use topic-owning subagents when available, while Codex Cloud uses its actual available workers. Grok CLI uses the same local-worker procedure only when supported, but cannot use computer-use features and requires smaller, concrete, well-verified tasks because its model is less capable. Grok bot cloud follows the cloud-capability guard rather than Project/local procedures. For `-a`, plan the first ready wave and a durable repeated loop as described in [continuous development](continuous-development.md). Keep these axes independent: selecting a Project does not start a sweep, and continuous development does not grant merge authority. An explicitly requested equivalent workflow in ordinary language has its stated meaning; do not silently infer additional flags or permissions.

## Flag and lifecycle contract

| Flag | Planning effect | Implementation handoff effect |
|---|---|---|
| no flag and no explicit merge instruction | Plan and record scope, dependencies, tracking structure, verification and permissions. | Establish/reuse tracking, implement and verify, keep issues updated, and leave the PR and delivery issues open pending integration. |
| `-m` / `--merge` | Record the author's explicit request to merge after development. Planning never creates PRs or merges. | Establish/reuse tracking and keep it current. Complete eligible merges under repository policy after verification, review, approvals and current-head checks, including existing automatic website/service updates triggered by merging. Close fully completed children after confirmed integration, then eligible parents. Separate deployment or release actions need their own authorization. |
| `-is` / `--issuesweep` / `--issue-sweep` | Triage the requested backlog with a bulk checkpoint and named task groups. | Track and implement only the accepted scope in dependency order; reuse selected original issues and preserve unrelated coordination. |
| `-isask` / `--issue-sweep-ask` | Revisit postponed candidates with the interview checkpoint; wins over `-is`. | Same tracking and implementation lifecycle for accepted scope only. |
| `-pr` / `--prototype` | Iterate in Chat until the user accepts a UI direction; record decisions and artifacts. | Record and implement the accepted direction using repository architecture and verify its UI states. |
| `-zip` / `-dropbox` / `-temp` | Choose how session files reach the implementer; combinable. With none, ask once at delivery time. `-temp` is the only planning-side GitHub write. | The prompt names the matching locator: the unpacked ZIP path, the Dropbox / `$DROPBOX_CCLOGS_DIR` path, or the draft PR branch to adopt as base, with `_temp-resource/zdev-<slug>/` removed before merge. |
| `-cccp` (also written `- cccp`) | Add Claude Code Cloud using the Project feature to the allowed set. | Apply Project manager/child-session instructions only if selected. |
| `-coc` | Add Codex Cloud to the allowed set. | Use only its actual tools and workers if selected. |
| `-cowsl` / `-comac` | Add Codex local CLI on WSL / Mac to the allowed set. | Use local topic-owning subagents if selected and supported. |
| `-ccwsl` / `-ccmac` | Add Claude Code local CLI on WSL / Mac to the allowed set. | Use local topic-owning subagents if selected and supported. |
| `-grmac` / `-grwsl` | Add Grok local CLI on Mac / WSL to the allowed set. | Prefer bounded daily tasks with explicit checks; no computer use; use subagents only if actually supported. |
| `-grc` | Add Grok bot cloud to the allowed set. | Use only confirmed cloud tools/workers, as for Codex Cloud; never assume local desktop or Project sessions. |
| `-a` | Inventory issues and PRs, distinguish current defects from landed fixes and acceptance holds, then provide the first ready wave and the continuous-loop contract. No redundant bulk approval for routine in-scope defects; an explicit interview still wins. | Repeat planning and development on any selected environment after each verified batch until a fresh sweep has no actionable in-scope work; reapply the environment filter at every wave. Preserve decision and other blocker records. No automatic merge, deployment or release authority. |

Combinations compose: `zdev -m -is` performs a bulk sweep and carries conditional merge authority; `-isask -m -pr` interviews first, prototypes selected UI topics, then hands off accepted scope. `zdev -cccp -a -m` targets the Project manager/child team, keeps sweeping and fixing, and conditionally merges eligible work. `-cccp -a` keeps implementation PRs and delivery issues open pending integration. `-cccp -comac` allows either Project or Codex local CLI on Mac; a mandatory Mac task selects Mac without injecting Project child-session instructions. `-cowsl -a -m` continuously handles only work fully completable on Codex local CLI on WSL, with conditional merge authority. Environment flags are deduplicated allowed candidates, not first-wins or last-wins routing, and do not themselves grant a sweep or merge. `-a -isask` interviews first and keeps unaccepted candidates held while continuing accepted work. `-grmac` and `-grwsl` constrain execution to Grok CLI on the respective OS; `-grc` targets Grok bot cloud. Treat these as allowed candidates, not implied merge or sweep commands, and never assume computer-use features for Grok CLI. Normalize the harmless spaced spelling `- cccp` to `-cccp`; explain other unknown flags instead of dropping them. Normalize flags in producer-side notes. In the final execution prompt, replace all flags with their plain-language scope and actions. Do not pass private commands, unsupported flags, plugin/app links, skill names or a requirement to invoke this workflow to the consumer.

The final prompt includes the actual repository URL and relevant existing issue URLs, target branch and inspected SHA, complete accepted scope and non-goals, task specifications and dependency order, tracking creation/reuse instructions, existing PR disposition, artifact access and exact-input needs, checks/current evidence and authorized lifecycle. Follow [the handoff rules](handoff.md). Keep the planning Chat and its permission boundary out of the execution prompt; its consumer needs only concrete instructions for its own session. Never invent issue IDs or URLs or claim future writes have already occurred.

## Implementation lifecycle carried by the prompt

Without merge authorization, open or update a reviewable PR, leave it open, and update each in-scope tracker, child and original issue with its PR URL and actual implementation/verification status. Delivery issues remain open pending integration. If `-m`/`--merge` is absent, do not infer merge intent from development, autonomy, green checks or the chosen environment; only an equally explicit user instruction can supply it.

With merge authorization, state a merge or hold decision for each PR. The author wants the merge completed after development, not just a merge-ready PR. Merge only eligible in-scope PRs after accepted work, review, required approvals, current-head required CI and repository policy are satisfied. Intentionally held and incomplete PRs remain open; partial integration can be correct when the plan says so. Record remaining gates in the issues. Close only fully satisfied in-scope children after confirmed integration, then parents whose entire accepted scope is complete. Keep unresolved originals and unrelated issues open. Creating a tracker, preparing a prototype, opening a PR or closing an unmerged PR is not delivery.

The requested merge includes updates to published websites or services automatically triggered by the repository's existing merge workflow. Inspect that workflow and disclose the known affected sites/services and automatic production effects in the handoff and before merging. Do not skip, downgrade to a merge-ready handoff, or ask for another generic merge/deployment approval solely because this expected automatic update occurs. Confirm the merge and report available automation results separately; a merged commit does not prove a successful deployment. Unknown or unavailable deployment status stays explicit.

This does not authorize separate deployment commands, release creation, manual plugin publication, changing deployment/security settings, or bypassing protected environments, review gates or access controls. Higher-priority safety requirements, actual tool permissions and explicit task-specific restrictions still apply. If a concrete conflict, materially different side effect or required approval remains, identify the exact action and blocker, ask only for the missing decision or approval, and continue independent work. Do not invent a blanket production-effect hold for an otherwise authorized merge.

After the final merge/hold decision, require the separate implementation agent to audit all resources actually touched, including pre-existing versus new diffs, open issues/PRs, local and remote branches, checkout state and owned worktrees. A clean and safely restored primary checkout is the goal, not permission to discard changes or delete a still-needed branch. The audit must be inlined in the standalone prompt for all environments, especially Grok local CLI. Require a child-to-parent manifest and safety-checked manager retry when a child (such as Cursor under a Grok bot manager) lacks remote deletion access; do not assume escalation can bypass repository policy. Follow [terminal resource cleanup](resource-cleanup.md) and report kept, deleted, failed and ambiguous resources. In continuous work, reconcile after each wave and at the terminal STOP. This is work for the **implementing session**; it never relaxes the read-only Chat planning boundary.

If a resource base PR already exists, inspect it and specify whether to adopt and update it; avoid duplicate PRs. Lasting files move into production locations and temporary resource paths are removed before merge. Link existing durable resources directly. Keep oversized generated files local/ignored; never use Git LFS. Do not infer permission to message people outside the requested GitHub workflow.

## Observation routes

The ChatGPT plugin's `zstatus` / `zwatch` observation routes are not part of this port. Use `/watch-ci` or the session tools for observation; they grant no planning or implementation authority.
